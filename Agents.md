## Important local fixes needed on a modern Linux host

These are environment compatibility fixes for the local ESP-IDF checkout, not firmware behavior changes.

### 1. ESP-IDF Python env creation

`tools/idf_tools.py` in ESP-IDF 3.3.1 uses `virtualenv --no-site-packages`, which fails with modern virtualenv.

Local fix applied in the ESP-IDF clone:

- remove `'--no-site-packages'` from `tools/idf_tools.py`

### 2. `pkg_resources` import

Modern setuptools removes `pkg_resources` unless pinned below `81`.

Inside the IDF virtualenv:

```bash
pip install "setuptools<81"
```

### 3. kconfig ncurses check false negative

The local host had working `ncurses`, but `tools/kconfig/lxdialog/check-lxdialog.sh` still failed.

Local fix applied in the ESP-IDF clone:

- replace the `check()` body with `exit 0`

### 4. Project Python interpreter setting

This repo had legacy Python 2 config values.

Updated files:

- `sdkconfig`
- `sdkconfig.defaults`

Set:

```text
CONFIG_PYTHON="python"
```

### 5. MQTT compatibility fix

`main/core/mqtt/mqtt.c` used `MQTT_EVENT_ANY`, but the `esp-mqtt` bundled with ESP-IDF 3.3.1 does not define it.

Fix applied:

- removed the `case MQTT_EVENT_ANY` branch
- the same fix was also applied to `main/core/mqtt/mqtt.c.template` so `update_templates.sh` does not reintroduce it

## Important maintenance OTA behavior

`scripts/build_maintenance_ota.sh` forces a one-time SPIFFS format by changing:

- `SGL_FORCE_SPIFFS_FORMAT_ONCE` to `1`

As a result, after maintenance OTA the controller firmware may boot correctly but `/fs/app.html` can disappear until the web UI is uploaded again.

This is expected behavior for the maintenance build.

## SPIFFS file replacement fix

The controller firmware originally failed replacing existing files after OTA with:

- `500 Failed to create file`

This was fixed in:

- `main/core/httpd/httpd_fs.c`

Fix:

- `unlink(filepath);` before `fopen(filepath, "w")`

This restored reliable replacement of `config.json` and `app.html` over Wi-Fi.

## Restoring the web UI after maintenance OTA

Regenerate UI payload:

```bash
cd /home/alan/sources/SuperGreenOS
bash ./update_htmlapp.sh config.controller.json
```

Upload over Wi-Fi:

```bash
bash ./upload_htmlapp.sh 192.168.1.104 ./spiffs_fs
```

Successful responses observed:

- `@FS File uploaded successfully`

Current reliable restore sequence on the legacy controller:

1. delete old `/fs/app.html`
2. delete old `/fs/config.json`
3. upload new `app.html`
4. upload new `config.json`

If `config.json` is uploaded first, `app.html` can appear to upload successfully but still end up truncated in SPIFFS.

## Legacy SPIFFS size constraints

The controller's SPIFFS partition is only `0x8000` (`32 KB`), so UI size matters.

Important discoveries:

- `html_app/style.custom.css` accidentally contained a second full copy of `normalize.css`
- `html_app/index.html` was already including `normalize.min.css`
- removing the duplicate CSS was required to make the compressed UI fit again

The upload helper was also improved:

- `upload_htmlapp.sh` prefers `zopfli` when available
- `SGL_GZIP_PYTHON` can point to a Python with `zopfli.gzip`
- fallback remains deterministic `gzip -9 -n`

This matters because a few hundred bytes can decide whether `app.html` fits in the legacy SPIFFS partition.

## Browser cache pitfall

Even when `app.html` was uploaded successfully, browsers could continue showing the older UI from cache.

Mitigation applied:

- `main/core/httpd/httpd_fs.c` now sends `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`
- it also sends `Pragma: no-cache`
- and `Expires: 0`

Important nuance on this legacy firmware:

- `/fs/app.html?<anything>` is not supported and returns `404`
- use plain `/fs/app.html`
- rely on the no-cache headers plus a hard refresh or incognito window if needed

Practical effect:

- reloaded `/fs/app.html` and `/fs/config.json` should reflect the latest upload instead of silently serving stale cached UI

After this, the admin UI at `/fs/app.html` was restored.
